# Development and verification

This repository is a Nim package whose executable entrypoint is `src/parun.nim`. Local development uses Nim 2.4.0, and the release workflow is pinned to Nim 2.4.0. The package manifest currently declares Nim `>= 2.2.0`, enables the `src` source directory, and defines the release build tasks in `parun.nimble`. `nim.cfg` enables threads and release optimization/linker settings.

## Local prerequisites

Install:

- Nim 2.4.0 and Nimble;
- a C compiler and linker;
- the runtime commands needed for the source operations you want to use: `pacman`, optionally `paru` or `yay`, `nimble`, `curl` for Nimble details and remote metadata refreshes, and `gunzip` for compressed index refreshes.

The source and terminal layers use POSIX/Linux interfaces. Package operations also expect the corresponding Arch or Nimble data directories and command permissions to be available at runtime; compilation does not require a live package database.

## Formatting and static checks

Run the Nim formatter in check mode over the maintained Nim sources from the repository root:

```bash
nph --check $(rg --files src tests tools benchmarks -g '*.nim' | sort) parun.nimble
```

To format the maintained Nim files in place, run `nph` with the repository's normal file-selection policy and review the diff before building. Generated files under `nimcache`, `bin`, `tools/output`, and compiled test/tool executables are build artifacts and are not documentation inputs.

## Build tasks

The manifest defines release builds and explicit verification tasks:

```bash
nimble native
nimble baseline_x86_64
nimble baseline_x86_64_v3
nimble verify
```

`native` writes the local optimized executable to `parun`. The two baseline tasks write release artifacts under `bin/`; the generic x86-64 task also checks the resulting ELF notes and disassembly for forbidden non-baseline instructions. These task descriptions and output paths are defined in `parun.nimble`, not inferred from this document.

`nimble verify` runs the whitespace check, manifest validation, every standalone test, the fixture-driven `--headless` CLI smoke test, measurement-tool compilation, and API documentation generation. `nimble release_verify` adds the native, portable x86-64, and x86-64-v3 release builds.

## Tests and module checks

The repository keeps tests as standalone Nim programs under `tests/`. Compile and run every test with the same source path and memory manager used by the project checks:

```bash
for test in tests/test_*.nim; do
  name="/tmp/parun-${test##*/}"
  name="${name%.nim}"
  nim c --path:src --mm:arc -o:"$name" "$test" && "$name"
done
```

The current test programs cover detail-cache behavior, stale detail-generation rejection, headless detail resolution, Nimble metadata parsing, the Pacman local database parser, v7 `.prix` validation and corruption handling, transaction command construction, terminal text wrapping, and bounded worker-process output. `tools/headless_cli_smoke.nim` additionally runs the built executable against a disposable v7 fixture and checks both successful and unavailable-index JSON results. `nimble check` validates the package manifest and its declared Nim dependency; it is not a substitute for the standalone test loop.

The public diagnostic commands are intentionally bounded and terminal-free:

```bash
parun --headless --nimble --index-dir=/path/to/indexes --headless-query=nph --headless-rounds=1
parun --headless-detail=nimble/nph --index-dir=/path/to/indexes --headless-timeout-ms=12000
```

Search diagnostics return `parun_headless_search` JSON. Detail diagnostics return `parun_headless_detail` JSON with a `status` and, on failure, an `error_kind` such as `index_unavailable`, `missing_package`, `worker_error`, or `timeout`. Older `.prix` format versions are not compatibility inputs; a v5/v6 file is an unsupported index and must be regenerated by the current builder.

## Documentation generation

Generate Nim API documentation into a disposable directory so generated HTML does not become a source-of-truth copy of the API:

```bash
DOC_OUT=$(mktemp -d /tmp/parun-docs.XXXXXX)
nim doc --project --index:on --outdir:"$DOC_OUT" src/parun.nim
```

Inspect the generated index and pages for the exported entrypoint and domain modules. The narrative documentation in `README.md` and `docs/` is maintained in the repository; the temporary directory is generated output.

## Maintainer checklist

For a source or API change:

1. Update the nearest module overview and exported contract documentation when the ownership or behavior changes.
2. Update `README.md` or the relevant guide when a user-facing command, prerequisite, key, path, or workflow changes.
3. Run the formatter command above, `nimble check`, all standalone tests, and the three manifest build tasks when the toolchain and host support them.
4. Generate and inspect Nim docs.
5. Use `git diff --check` and review generated/untracked artifacts before handing off the change.

The documentation should state a measured result only when the command or benchmark that produced it is named. Source-level capacities, format versions, and option behavior should remain linked to the defining module or manifest.

## Tools and benchmark probes

The standalone programs under `tools/` and `benchmarks/` are maintained developer workflows, not runtime dependencies:

- `tools/build_indexes.sh [output-dir]` compiles `tools/build_indexes.nim` and writes selected source `.prix` indexes to the requested directory;
- `tools/byte_accounting.sh` writes owned-capacity measurements to `tools/output/byte_accounting.json`;
- `tools/measure_baseline.sh` builds a release binary and writes baseline process measurements to `tools/output/baseline.json`;
- `tools/detect_cpu.nim` reports the compiler flags selected by the CPU probe;
- `benchmarks/` contains standalone probes for index residency, detail-worker memory, native Pacman/Nimble paths, search scoring/sorting, selection, and terminal/source parsing. The NOD probes share `benchmarks/nod_harness.nim`.

The index residency probe compares an eager deep-open path with deferred section proofs in fresh processes. Build its deterministic fixture in a separate process so builder allocations do not contaminate the measurement, then run both modes against the printed directory:

```bash
nim c -d:release --mm:arc --path:src --path:benchmarks -o:/tmp/parun-bench-nod-memory benchmarks/bench_nod_memory.nim
NOD_MEM_BUILD_ONLY=1 /tmp/parun-bench-nod-memory
NOD_MEM_OPEN=eager /tmp/parun-bench-nod-memory /path/to/fixture-dir
NOD_MEM_OPEN=lazy /tmp/parun-bench-nod-memory /path/to/fixture-dir
```

Each JSON phase reports mapped-file residency plus RSS, PSS, anonymous RSS, file RSS, and private dirty memory. Compare `after-open`, proof stages, `hot-sweep`, and `cold-detail-sweep` using the same fixture and build. The detail-worker probe additionally emits its owned cache metrics after a detail response or diagnostics request; its optional arguments are `NAME REPO SOURCE URL`, where `SOURCE` is `system` or `nimble`. Set `PARUN_DETAIL_POLL_LIMIT` above its default of 500 when measuring a slow remote fallback path.

To measure the interactive details lifecycle in a real PTY, compile `tools/measure_baseline.nim` and run `tools/measure_baseline --details-no-animation --binary=/absolute/path/to/parun --output=/tmp/parun-details.json --perf-output=/tmp/parun-details.perf.json`. The details mode uses a 120x32 PTY, searches for `aur/paru`, sends F1, waits for request/cache/wrap/reveal transitions, toggles the panel off and on again, and records parent RSS/PSS plus descendant-process peaks. Use `--details-local` to measure the mapped Pacman package `local/7zip`, `--details-nimble` to measure `nimble/nph`, `--details` to retain the normal reveal animation, or `--details-no-trace` to measure the parent without lifecycle tracing. Set `PARUN_DETAIL_TRACE` only when running the executable directly; the harness sets it automatically and stores newline-delimited lifecycle events beside the requested JSON output.

The details harness also records `/proc/<pid>/smaps` mapping totals at the selected, request, loaded, settled, and cached-reopen points. These measurements distinguish demand-paged index residency, virtual thread-stack reservation, and shared runtime pages from retained detail data; they do not support calling the transition a payload leak.

Use `tools/measure_sweep.nim` after building one identified release binary to repeat fresh-process measurements and report minimum, median, maximum, and spread without imposing an arbitrary threshold:

```bash
nimble native
nimble measure_sweep
/tmp/parun-measure-sweep --harness=/absolute/path/to/tools/measure_baseline --binary=/absolute/path/to/parun --index-dir=/absolute/path/to/indexes --samples=5 --output=/tmp/parun-aur-sweep.json
/tmp/parun-measure-sweep --harness=/absolute/path/to/tools/measure_baseline --binary=/absolute/path/to/parun --index-dir=/absolute/path/to/indexes --details-nimble --samples=5 --output=/tmp/parun-nimble-sweep.json
```

`--details-trace` enables lifecycle tracing for either command, and `--details-local` selects the local Pacman path; the sweep records the selected source in its JSON output.

On the 2026-09-22 Linux x86-64 run used for this repository state, the final three-sample no-trace sweep measured local `7zip` at 3,496–3,628 KiB idle RSS and 4,008–4,168 KiB after details; median RSS increased from 3,504 KiB to 4,032 KiB and median PSS increased from 1,397 KiB to 1,869 KiB. AUR `paru` measured 4,844–4,880 KiB idle RSS and 8,000–8,036 KiB after details; median RSS increased from 4,860 KiB to 8,016 KiB and median PSS increased from 2,733 KiB to 5,655 KiB. Nimble `nph` measured 3,036–3,092 KiB idle RSS and 3,680–3,808 KiB after details; median RSS increased from 3,092 KiB to 3,804 KiB and median PSS increased from 939 KiB to 1,530 KiB. These are host-specific observations, not release budgets; repeat the sweep on the target runner before adding a gate.

The trace-enabled three-sample sweep measured local at 3,632–3,684 KiB idle RSS and 4,168–4,224 KiB after details, AUR at 4,884–4,928 KiB idle RSS and 8,036–8,076 KiB after details, and Nimble at 3,112–3,168 KiB idle RSS and 3,704–3,888 KiB after details. Their median PSS values moved from 1,533 to 2,021 KiB, 2,777 to 5,693 KiB, and 983 to 1,513 KiB respectively. These are host-specific observations, not release budgets; repeat the sweep on the target runner before adding a gate.

To measure the staged Nimble path, build the harness with `nim c --path:src tools/measure_baseline.nim`, refresh a temporary Nimble index with `./parun --internal-refresh-indexes --refresh-sources=nimble --index-dir=/tmp/parun-nimble-index`, and run `tools/measure_baseline --details-nimble --details-no-animation --index-dir=/tmp/parun-nimble-index --binary=/absolute/path/to/parun --output=/tmp/parun-nimble-details.json --perf-output=/tmp/parun-nimble-details.perf.json`. The harness searches for `nimble/nph`, records the immediate `details-summary-cached` event, then waits for `details-cache-updated` from the full manifest enrichment. The first cold view therefore reports one detail request even though the registry summary is local; a fresh process with a valid sidecar should still complete the enrichment without a repository fetch. The previously recorded 21 ms zero-request result describes the pre-enrichment implementation and is retained only as historical evidence, not as the current behavior. Repeat measurements after the sidecar has been populated and report the summary-to-manifest transition separately from the initial registry-summary latency.

Benchmark JSON and compiled tool outputs belong under the existing output or temporary directories. They are evidence artifacts, not API documentation and should not be summarized as a performance claim without recording the command, host, input fixture, and result.
